# Tiles render off the UI thread; in the browser, in a render worker

Issue #357: scrolling stuttered in the MAUI viewer and in the Blazor demo on phones because document work ran on the UI loop. Every shell now keeps the UI thread to planning frames, presenting finished tiles and drawing scaled placeholders.

Where the host has threads (MAUI, desktop), a background `TileScheduler` queues each tile job on the thread pool, and the whole job runs there: page load, display-list build, render and present. Surfaces are therefore called on workers (`IRenderSurface` documents it); the MAUI surface makes its Skia image on the worker and queues it for the UI thread. Page models a shell needs (annotations, selectable text, the accessibility layout) are built on workers too. The thread-safety contract (concurrent reads and renders, single-threaded mutation) is enforced by the session: reads on workers take a read lease, and `DocumentSession.BeginEdit`, which `AnnotationLayer` takes around every edit, cancels the reads in progress, waits for them to stop and holds new ones until the edit ends; cancelled reads start again afterwards. Replays of finished display lists read no document objects and are not held.

In the browser the runtime is single-threaded. We add a viewer extension point, `IRemoteTileRenderer` (`ViewerOptions.UseRemoteRenderer`), for tiles drawn outside the viewer's thread, with one implementation: the Blazor package's render worker, a module Web Worker that boots the app's own .NET runtime a second time (the same framework files, so nothing extra is downloaded), opens its own copy of the document (from the same bytes, or the same address through range requests), and returns each content tile as a transferable `ImageBitmap`. The scheduler hands it the tiles it accepts (content layers) and draws the rest itself, so annotation and form-field overlays, which edits change, stay with the session's own document and never wait for the worker. The worker is strictly an app opt-in: the library never starts it by itself. An app serves it from `Main` (`RenderWorker.Serve`), starts it (`RenderWorker.StartAsync`) and gives each session a renderer (`ViewerOptions.UseRemoteRenderer(RenderWorker.Open(...))`); without all three, or without Web Workers, everything is drawn on the page's thread as before. The demo opts in (`?worker=0` turns it off).

## Consequences

The render worker costs a second runtime: its boot time and memory are measured in `docs/benchmarks/viewer-render-worker.md`, next to the frame times with and without it. The default path (no worker) is to be made smooth on its own by follow-up work: scaled image decode (#362), browser-native image decode, and sliceable decode, so that the worker stays an option for the heaviest documents rather than a requirement.

## Considered Options

- .NET WebAssembly multithreading (`WasmEnableThreads`): rejected for now. It needs `SharedArrayBuffer`, so the page must be cross-origin isolated (COOP `same-origin` + COEP `require-corp`); GitHub Pages sends neither header (measured on the project's Pages site) and static hosts in general cannot be configured, and `require-corp` also blocks cross-origin documents and images that do not opt in. Under isolation the demo boots, but .NET then runs on a worker ("deputy") thread and the page cannot call synchronous `[JSExport]` methods, which the viewer's input handling relies on to decide `preventDefault` (measured: "Cannot call synchronous C# methods" on every pointer and key event). Moving the interop to asynchronous calls would cost the viewer its synchronous gesture decisions.
- OffscreenCanvas with WebGL in the worker: deferred. The worker uses the software rasterizer; the WebGL backend (ADR 0012) stays on the page's thread when selected.
- Text selection and the accessibility layout in the worker: deferred. They build structures the page's thread uses directly; with a render worker the Blazor shell starts them only once the view has been still for 300 ms, so they do not run during a scroll.
