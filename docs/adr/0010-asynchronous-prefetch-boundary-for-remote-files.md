# Remote files are read synchronously behind an asynchronous prefetch boundary

The spec keeps the core synchronous, with `Async` only at the open and save boundaries, and commits to Blazor WebAssembly, where nothing may block on HTTP. A range-request source (viewer capability 5, issue #207) breaks the assumption behind that rule, that once a document is open every byte is a cheap read away. We keep the core synchronous and add one more asynchronous boundary instead of making reading asynchronous: `PdfEngine.OpenAsync(HttpClient, Uri)` fetches the tail, the structure, the catalog and the page tree before it returns, and `PdfPage.PrefetchAsync` fetches the objects a page's interpretation needs (its object closure, without other pages) before the caller reads it synchronously. Both are the ordinary synchronous code run without blocking: a read that misses throws an internal miss, the boundary fetches the missed range (up to the next object's offset, from the cross-reference table) asynchronously and in parallel with the other misses of the same round, and runs the code again; caches never keep a miss, and an open attempt that misses is dropped with its diagnostics, so the observer sees each diagnostic once. Outside a boundary, a synchronous read that misses blocks on the request where the platform can (`PdfOptions.SynchronousRangeFetch`, on by default), and on the browser, where it cannot, fails with `PdfRangeNotLoadedException` naming the prefetch to await. Fetched bytes sit in a cache of fixed-size blocks bounded by `RangeCacheLimit`; parsed objects stay in the document's object cache as for any source.

## Considered Options

- An asynchronous read path through the parsers, interpreter and model (`ValueTask` everywhere): rejected because it doubles every API or makes every synchronous caller pay for state machines on the hot paths the spec requires to allocate nothing, for the benefit of one source.
- Blocking everywhere, including the browser (sync-over-async): rejected because the browser's single thread deadlocks, which is exactly the platform the source exists for.
- Prefetching by byte ranges computed from the cross-reference table alone, without parsing: rejected because which objects a page needs is only known by following its references, and an indirect `Length` or an object stream can only be found by parsing.
- Downloading the whole file at open: kept only as the fallback for servers without range support.
