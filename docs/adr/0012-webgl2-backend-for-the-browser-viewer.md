# The browser viewer gets an optional WebGL 2 backend; WebGPU later

Issue #353 asks whether the Blazor WebAssembly viewer should draw on the GPU. ADR 0006 makes this a backend question (backends consume display lists) and ADR 0001 lets a backend depend on its platform library and nothing else; in the browser the platform library is the browser itself. We add `Broadside.Rendering.WebGL`, a backend that replays a display list into WebGL 2 through one JavaScript module of our own (`broadside-webgl.js`, no third-party script), and the viewer's `WebGLTileBackend`, selected with `ViewerOptions.UseBackend(WebGLTileBackend.Create)`. The software rasterizer stays the default.

The replay is recorded in .NET and submitted in one interop call per tile, because a call per operation would cost more than drawing it: fills and glyph outlines are drawn by stencil-then-cover (the winding in seven stencil bits, non-zero by increment and decrement on the two faces, even-odd by inversion), strokes are tessellated in .NET (quads, joins, caps and the dash walk follow the rasterizer's rules, including stroke adjustment and zero-length dashes) and drawn in a union stencil mode, the clip is the eighth stencil bit (re-established from the clip stack after a restore), images and stencil masks are mipmapped textures cached across tiles and zoom levels under a byte budget, and flattened glyph outlines are cached per font program, glyph and size class. Anti-aliasing is 4x multisampling. Tiles go GPU to GPU from the WebGL canvas into the viewer's tile canvases; `WebGLRenderer.Render` reads the pixels back for callers that need a `Bitmap`.

What the GPU path does not draw goes to the software rasterizer, never silently: a transparency group that is not plain (opacity below 1, a soft mask, knockout) is rasterized by `SoftwareRasterizer.Render(in DisplayGroup, ...)` into a texture (`BackendTransparencyGroupRasterized`); shadings, tiling patterns, blend modes other than Normal, a soft mask in the graphics state, an annotation composited with opacity or a blend mode, an image whose mask has another size, and an image larger than the largest texture make the software rasterizer draw that tile (`BackendShadingRasterized`, `BackendTilingPatternRasterized`, `BackendBlendModeRasterized`, `BackendSoftMaskRasterized`, `BackendAnnotationRasterized`, `BackendImageMaskRasterized`, `BackendImageTooLarge`); without WebGL 2 every tile is the rasterizer's (`BackendWebGLUnavailable`). Native shadings and blend modes in shaders are follow-ups, not decisions.

WebGL 2 rather than WebGPU, for reach: WebGL 2 runs in every current browser, Safari and iOS since 15, and headless Chromium in CI through SwiftShader, while WebGPU is still missing or behind flags on many phones and older iOS versions the hosted demo is opened on. The recorder's output (triangles, stencil passes, textured quads) maps directly onto a WebGPU render pass, so a WebGPU path can be added behind the same module later if compute-based coverage (exact anti-aliasing) turns out to be worth it.

The software rasterizer stays the default because the gain is real but uneven (docs/benchmarks/viewer-gpu-vs-software.md): large on slow CPUs and on image pages, small on a fast desktop with the AOT build, and none on pages drawn mostly by the fallbacks; and because 4x multisampling is coarser than the rasterizer's exact coverage on small text (the `webgl` rows of `GoldenThresholds`).

## Considered Options

- SkiaSharp's WebAssembly build: rejected. Its native library is linked into `dotnet.native.wasm`, which needs the native relink of an AOT build on every app, adds several megabytes to a download the demo already struggles to keep under its budgets, and conflicts with the Blazor package's "no native assets" promise; the gain over our own WebGL path would be its shading and blend-mode coverage, which we can add in shaders.
- Canvas 2D (`Path2D`, `drawImage`): rejected as the backend because each display-list operation would be an interop call, and its anti-aliasing and compositing cannot be matched to the rasterizer's; it remains how tiles reach the screen.
- Rendering in a worker with OffscreenCanvas: deferred; the WebAssembly build is single-threaded, and the cooperative tile scheduler already slices recording.
